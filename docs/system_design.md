# システム構成

## 方針

- **速さが要る所はRust**：ルール・MCTS・自己対局。1局約300手 × 1手あたり数百回の評価を、数万〜数十万局回すため。
- **研究・学習はPython**：PyTorchでの学習、実験の指示、集計、グラフ。RustのコアをPythonから呼べるモジュール（PyO3）にして、Pythonからも局面を作ったり指し手を調べたりできるようにする。
- **推論はONNX Runtime（CUDA）**：PyTorchで学習した重みをONNXに書き出し、Rustの自己対局プロセスがGPUで推論する。自己対局中にPythonを経由しない。
- **既存のJSは照合元・比較相手として残す**。UIは当面そのまま。

C++ではなくRustにする理由：Windowsでのビルドと依存管理（cargo）が楽、PyO3でPythonから呼べる、ONNX Runtimeのバインディング（`ort` クレート）がある。速度はC++と同等。

## ディレクトリ構成（予定）

```
shogi3/
├── (既存) *.js, shogi3.html, tools/       … 現行ゲームと手作りエンジン。照合元・比較相手
├── docs/                                  … この設計書
├── engine-rs/                             … Rustワークスペース
│   ├── core/        (crate: shogi3-core)  … 盤面・指し手生成・指す/戻す・終局判定・ハッシュ
│   ├── mcts/        (crate: shogi3-mcts)  … 3人用MCTS・評価器インターフェース・バッチ推論
│   ├── selfplay/    (bin)                 … 自己対局ワーカー（多数の対局を並行、ONNXで推論、学習データを書き出す）
│   ├── arena/       (bin)                 … 評価対局（ネット同士、ネット vs 基準エンジン）
│   └── py/          (crate: pyo3モジュール) … Pythonから core / mcts を呼ぶ
├── python/
│   ├── shogi3ml/    … モデル定義・データ読み込み・学習・ONNX書き出し
│   ├── scripts/     … 学習ループの実行、評価、分析
│   └── notebooks/   … 分析用（任意）
├── runs/            … 実行ごとの成果物（git管理外）
│   └── <run名>/
│       ├── config.toml
│       ├── models/      … 世代ごとの .pt と .onnx
│       ├── selfplay/    … 学習データ（シャード）
│       ├── eval/        … 評価対局の結果
│       └── logs/
（照合用データは engine-rs/core/tests/fixtures/ に `node tools/gen-fixtures.js` で作る。git管理外）
```

## データの流れ

```
          ┌──────────── 最新の model.onnx ─────────────┐
          ▼                                             │
 selfplay（Rust, GPU推論）                               │
   数百局を並行して進め、局面をまとめて推論                │
          │ 学習データのシャード (runs/<run>/selfplay/)   │
          ▼                                             │
 training（Python, PyTorch, GPU）                        │
   直近のデータ窓から学習 → 一定ステップごとに書き出し ────┘
          │
          ▼
 arena（Rust）… 定期的に 新モデル vs 旧モデル / 基準エンジン
```

- 自己対局と学習は**非同期**（KataGoと同じ）。自己対局は常に最新のモデルを使い、学習は溜まったデータから続ける。
- GPUは1枚なので、自己対局の推論と学習が同じGPUを使う。最初は交互に回す（自己対局 N局 → 学習 M ステップ → 書き出し）同期版で作り、ボトルネックを見てから非同期にする。

## JSとの照合

- `tools/gen-fixtures.js` がJS実装（`applyMove` / `allMoves`）で乱数の対局を指し、毎手の合法手の集合・指した手・指した後の局面（ダイジェスト）と、終局結果（勝者・終局の種類・手数）を書き出す。進め方を3種類（駒取り優先／玉を前進／玉を取らない）に分け、脱落・入玉・500手制限をすべて通す。
- Rust側のテスト（`engine-rs/core/tests/js_fixtures.rs`）がこれを1手ずつ再生して照合する。
- 取り駒ルール3種すべてで行う（各300局・計約14万手で一致を確認済み）。
- 旧エンジンの照合で使った方式（`tools/verify-engine.js`）と同じ考え方。

## 基準エンジン（比較相手）

- 学習の進み具合を測るため、手作りエンジン（`engine.js`、パラノイド＋α-β）と対戦させる。
- 方法は2つ。どちらにするかは open_questions.md で決める。
  1. **JSのまま使う**：Nodeプロセスを立て、標準入出力で局面を渡して指し手を返させる。移植不要だが遅い（1手2秒の設定なら1局10分）。
  2. **Rustに移植する**：評価関数と探索を移植。照合は既存のJSエンジンと深さ固定の探索値で行う（`verify-engine.js` と同じ方法）。
- 弱い比較相手として、ランダム、1手読みの駒得優先もRustで用意する（学習初期の進み具合を見るため）。

## 性能の目安（見積もり。フェーズ1〜3で実測して更新する）

- ネット：10ブロック×128チャンネル程度、入力9×9。RTX 3080・FP16・バッチ512で、推論はおおよそ毎秒数万局面と見込む。
- 自己対局1局：約300手 × 平均約225回の評価（下記のプレイアウト数ランダム化を入れた場合）≈ 約7万回の評価 → 1局あたり数秒。
- 目安：1日あたり数万局。10万局まで数日。
